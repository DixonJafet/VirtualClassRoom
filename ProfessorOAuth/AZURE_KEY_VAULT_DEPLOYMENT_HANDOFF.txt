MCP + OAUTH ON AZURE — IMPLEMENTATION GUIDE For an existing ASP.NET Core
/ C# application with existing users

GOAL Let a user sign in to your website’s existing account and then
authorize Claude, ChatGPT, or another compatible MCP client to use your
remote MCP server.

RECOMMENDED AZURE ARCHITECTURE

1.  Auth/API application (ASP.NET Core)
    -   Keep your existing users, user database, password verification,
        and website login.
    -   Add OpenIddict to this application as the OAuth 2.1 / OpenID
        Connect authorization server.
    -   Reuse the existing login session/cookie for the browser-based
        authorization step. Do not make users create a second account.
    -   Store OpenIddict application, authorization, and token records
        in your existing database (or the same Azure SQL database).
2.  MCP application (ASP.NET Core)
    -   Host the MCP endpoint on Azure App Service.
    -   Expose Streamable HTTP, for example: https://mcp.example.com/mcp
    -   Validate OAuth access tokens issued by your authorization
        server.
    -   Use the token’s subject/user ID to access only that user’s
        permitted data.
3.  Azure services
    -   Azure App Service: host the Auth/API app and MCP app. They may
        be separate App Services or separate apps initially; keep the
        public HTTPS URLs stable.
    -   Azure SQL Database: use your existing database if it is already
        hosted there; otherwise retain your current database and connect
        securely.
    -   Azure Key Vault: store signing/encryption certificates and other
        secrets.
    -   App Service Managed Identity: let each app access Key Vault
        without storing Key Vault credentials in configuration.
    -   Application Insights: monitor authentication and MCP errors.

IMPORTANT: OpenIddict is a framework, not a hosted OAuth service. You
deploy and configure it inside your ASP.NET Core application. OpenIddict
provides OAuth and OIDC server functionality, but do not assume it
automatically implements MCP-specific CIMD client discovery/validation.
That part must be implemented and tested separately or provided by a
compatible authorization-server implementation.

IMPLEMENTATION STEPS

STEP 1 — PRESERVE YOUR EXISTING USERS - Do not migrate, duplicate, or
recreate your users. - Keep your current user table and existing
password-hashing/verification logic. - Connect OpenIddict to the
existing user system. If you use ASP.NET Core Identity, integrate it
directly. If you use custom authentication, implement the OpenIddict
authorization flow so it authenticates users through your existing login
system. - Keep your current website session cookie for browser login.
The MCP client must never receive the website cookie or the user’s
password.

STEP 2 — ADD OPENIDDICT TO THE AUTH APPLICATION - Add the OpenIddict
ASP.NET Core and Entity Framework Core packages. - Configure OpenIddict
Server with: * Authorization Code flow. * PKCE with S256 required. *
Refresh tokens, with rotation/reuse protection. * HTTPS metadata and
endpoints. * A dedicated MCP audience/resource and limited scopes. - Add
the OpenIddict database tables using EF Core migrations. - Configure a
persistent signing certificate and encryption certificate. Do not use
temporary/development certificates in production. - Put production
certificates/secret material in Azure Key Vault. Enable Managed Identity
on the App Service and grant it only the required Key Vault permissions.

STEP 3 — IMPLEMENT THE USER CONSENT PAGE - When an MCP client starts
OAuth, send the user to your authorization endpoint. - If the user is
not logged in, redirect them to your existing login page. - After login,
show a consent page identifying the client (for example, Claude or
ChatGPT) and the requested permissions. - Let the user approve or deny
access. - Record the authorization and scopes for that user. - Support
revocation: users must be able to revoke an MCP client’s access.

STEP 4 — ISSUE MCP-SPECIFIC TOKENS - After consent, issue an OAuth
access token for the MCP API. - Include a stable user identifier in the
“sub” claim. - Set the audience (“aud”) specifically to your MCP API. -
Include only approved scopes, for example: mcp:profile.read
mcp:orders.read - Use short-lived access tokens (for example, 10–15
minutes). - Use refresh tokens only if needed by the client; rotate them
and revoke them when access is revoked. - Do NOT reuse your website’s
existing JWT as the MCP access token unless it is deliberately
redesigned for this audience and OAuth purpose. Do not accept website
session cookies at the MCP endpoint.

STEP 5 — PROTECT THE MCP SERVER - Require a valid Bearer access token
for every protected MCP request. - Validate signature, issuer, audience,
expiry, and scopes. - Obtain the user ID from the validated token’s
“sub” claim. - Enforce authorization in every tool/API operation. Never
trust a user ID supplied as a tool argument when it could be taken from
the token instead. - Ensure a user can only read or modify records they
are authorized to access. - Return HTTP 401 for missing/invalid tokens
and 403 for insufficient permission.

STEP 6 — IMPLEMENT MCP OAUTH DISCOVERY Your MCP server must publish
OAuth Protected Resource Metadata (RFC 9728), and your authorization
server must publish OAuth Authorization Server Metadata (RFC 8414) or
OpenID Connect Discovery metadata.
